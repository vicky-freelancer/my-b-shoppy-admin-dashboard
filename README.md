# MY B SHOPPY admin dashboard

Manage products, subcategories, orders, customers and analytics. Category dropdowns use the same ten-category order as the storefront.

## Run locally

1. Install Node.js 20.19+ or 22.12+ and run `npm install`.
2. Copy `.env.example` to `.env` if overriding settings.
3. Run `npm run dev`. This starts Express authentication and Vite together at `http://localhost:3000`.
4. Sign in using the configured user ID and password. The requested account ID is `myBadmin`; its password is stored as a server-side scrypt hash, never a browser-side constant.

Direct Vite development (`npx vite`) also serves the authentication routes. Restart the development server after changing its configuration. An HTML response from `/api/admin/login` means the request reached a frontend fallback instead of the authentication server; production hosting must route `/api/admin/*` to the Node server. Rebuild and redeploy if the browser still displays a raw JSON parsing error.

## Production

Run `npm run build`, then `npm start`. Use a Node host; static-only hosting cannot serve the authentication endpoints. Set `NODE_ENV=production` and serve through HTTPS so the Secure session cookie is sent. `PORT` defaults to 3000; `HOST` defaults to 0.0.0.0.

Authentication requests use the dashboard's own origin, including on `admin.mybshoppy.com`. Forward `/api/admin/*` to this Node server when using a reverse proxy. Remove any stale `VITE_ADMIN_API_URL` override and rebuild to use this default; a separate API origin requires its own credentialed CORS and allowed-origin configuration.

The auth server accepts `ADMIN_USERNAME` and `ADMIN_PASSWORD_HASH` overrides. The hash format is `salt:hex-digest`, generated by Node's `crypto.scryptSync(password, salt, 64)`. Keep credentials and overrides in host secrets, never `VITE_` environment variables. The shipped default digest matches the account requested for this project.

Sessions use random tokens in HttpOnly, SameSite=Strict cookies, expire after eight hours, and are revoked on logout. Sessions and login-attempt limits live in server memory: a restart signs users out. Use shared server-side storage before deploying multiple server instances. Five failed login attempts per IP temporarily block further attempts for fifteen minutes. No demo access, open signup, invalid-password fallback, or local-storage login is provided.

This account gates the dashboard UI. Existing Supabase calls continue to use the project's configured public client and database policies; this change does not alter or audit Supabase row-level permissions. Enforce permissions in Supabase for database-level authorization.

## Mobile behavior

Below 1024px, navigation opens as a drawer with a backdrop, Escape dismissal and keyboard focus containment. Content uses the full screen width. Tables scroll inside their own panels; form controls and actions wrap on narrow screens. Headings remain upright.

## Checks

- `npm run lint`
- `npm run test:auth` tests rejected credentials, sessions, forged cookies, logout revocation, origin rejection and login attempt limits using isolated credentials.
- `npm run build`

The sibling storefront repository contains the broader mock-data functional/browser harnesses and test report under `scripts/` and `reports/`. The browser suite requires Playwright and Chromium, a local admin server on port 3200 (or `ADMIN_QA_URL`), and the password in `ADMIN_QA_PASSWORD`. It intercepts Supabase requests and blocks live writes.
